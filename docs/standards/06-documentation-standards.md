# Documentation Standards

## 1. Documentation Purpose

Hagsyn 的文档不是装饰，而是产品边界、工程规则和设计共识的正式载体。当前文档体系需要同时支持：

- 日常开发参考
- 后续扩展时的边界判断
- 产品、工程、UX 三条主线的长期沉淀

## 2. Directory Responsibility

当前 `docs/` 下各目录职责如下：

### `docs/product/`

放产品层文档，例如：

- 产品定位
- 信息架构
- 模块职责
- 工具策略
- 路线规划

它回答的是“做什么、为什么做、先后顺序是什么”。

### `docs/standards/`

放工程与代码规范，例如：

- 工程原则
- 目录结构
- 前后端标准
- API 规则
- 数据建模规则
- 文档规则

它回答的是“怎么做、做到什么程度算一致”。

### `docs/ux/`

放视觉与交互规范，例如：

- 设计原则
- 视觉系统
- 布局导航
- 组件规则
- 工具工作区模式
- 空状态表达
- 品牌语气

它回答的是“界面和交互如何保持统一”。

### `docs/superpowers/`

放过程性材料，例如：

- design spec
- implementation plan
- 某次任务的执行上下文

它记录的是“这次任务怎么被思考和推进过”，不替代长期标准文档。

## 3. Naming Rules

标准主线文档采用：

```txt
NN-topic-name.md
```

例如：

- `00-engineering-principles.md`
- `04-api-standards.md`

规则如下：

- 使用两位数字排序
- 文件名用小写英文和 `-`
- 名称直接表达主题，不使用模糊标题

## 4. Writing Rules

文档内容应围绕当前项目真实边界，避免两类问题：

1. 写成泛化教程，脱离当前仓库
2. 写成只对单次任务有效的操作记录

推荐写法：

- 先写当前状态
- 再写当前规则
- 最后写可接受的未来扩展方向

## 5. Source Of Truth Rules

不同类型的信息应放在最合适的位置：

- 启动方式、基础使用说明：`README.md`
- 协作规则、代理执行约束：`AGENTS.md`
- 长期产品规则：`docs/product/**`
- 长期工程规则：`docs/standards/**`
- 长期 UI/UX 规则：`docs/ux/**`
- 单次任务 spec/plan：`docs/superpowers/**`

不要把长期规则散落在多个入口里重复维护。

## 6. Update Rules

以下情况应主动更新标准文档：

- 目录职责发生变化
- API 命名或鉴权方式变化
- 数据模型约束变化
- 前后端工程边界变化
- 产品已确认新的长期规则

以下情况通常不需要更新 standards，而应更新过程文档或实现本身：

- 一次性的调试记录
- 临时验证命令输出
- 尚未确认的想法

## 7. Relationship Between Docs And Code

文档不能替代代码，但必须与代码相符。

维护顺序建议：

1. 先确认真实实现和边界
2. 写或更新文档
3. 再让后续开发按文档执行

如果文档与实现冲突，以当前已验证实现为准，并尽快修正文档。

## 8. Change Review Checklist

新增或修改文档前，至少自查：

1. 是否引用了当前仓库真实结构和真实接口
2. 是否把未来设想错误写成当前现状
3. 是否写入了不该进入长期标准的一次性信息
4. 是否与 `README.md`、`AGENTS.md` 已有规则冲突

## 9. Language And Tone

当前项目默认使用简体中文书写普通说明，代码、路径、配置键名、API 名称保持原文。标准文档也遵循这条规则。

文风要求：

- 直接
- 准确
- 面向实际开发
- 少空话，少口号

## 10. Documentation Growth Strategy

后续文档扩展优先沿现有主线继续追加，不随意新开平行目录。只有在某一类内容长期稳定且明显超出当前目录承载能力时，才考虑继续细分。

文档体系本身也应遵守“小步迭代、真实需要驱动”的工程原则。
