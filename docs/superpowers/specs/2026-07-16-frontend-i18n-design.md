# Frontend I18n Design

## 目标

为 Hagsyn 当前前端补上最小可用的国际化能力，只覆盖前端界面文案，不改后端接口错误文案与返回消息。

本次设计目标是：

1. 支持 `zh-CN` 与 `en`
2. 首次进入时默认跟随浏览器语言
3. 用户可在前端界面中手动切换语言
4. 手动选择结果持久化保存
5. 保持现有工作台壳层、原生 ES modules 与无构建前端模式

---

## 一、范围边界

本次只做：

1. 前端界面文案国际化
2. 语言状态管理
3. 语言切换控件
4. 首次访问语言探测
5. 本地持久化

本次不做：

1. 后端 API 错误消息国际化
2. `Accept-Language` 请求头驱动的后端响应
3. 第三语言接入
4. 引入外部 i18n 库
5. 把整个前端重构为框架项目

---

## 二、产品落点

该能力不是一个独立模块，也不是新工具。

它应落在当前前端产品壳层内，服务以下既有模块：

- `Dashboard`
- `Tools`
- `Nodes`
- `Graph`
- `Roadmaps`
- 登录与注册视图
- 用户菜单、Modal、Toast、设置面板等公共交互组件

它的角色是“前端基础能力增强”，而不是新页面或新工作流。

---

## 三、推荐实现方案

推荐采用轻量字典方案。

### 方案说明

新增一个前端 `i18n` 模块，集中维护：

- 当前支持语言列表
- 浏览器语言探测逻辑
- 当前生效语言状态
- `localStorage` 持久化键
- `t(key)` 翻译函数
- 可选的模板插值能力

页面渲染与交互文案统一通过字典 key 取值，而不是继续在各模块中硬编码中英文文案。

### 推荐理由

1. 当前前端主要由 JS 模块动态渲染，字典取值比 DOM 扫描更自然
2. 可贴合现有 `config.js / components / views / tools` 分层
3. 不引入外部依赖，符合当前无构建静态前端模式
4. 后续若继续扩工具或补第三语言，不需要推翻结构

### 不推荐方案

不推荐把首版建立在全量 `data-i18n` DOM 扫描方案上，因为当前工具工作区、Toast、Modal、右侧说明等大量内容都来自 JS 动态模板，后续维护会别扭。

---

## 四、语言策略

### 支持语言

- `zh-CN`
- `en`

### 默认语言判定

首次访问且本地没有用户已选语言时：

1. 读取 `navigator.language`
2. 若以 `zh` 开头，则使用 `zh-CN`
3. 其他情况统一回退到 `en`

这样可避免在首版就处理过细的地区变体映射。

### 用户手动切换优先级

若用户已经在前端手动切换过语言，则始终优先使用本地持久化值，而不是再次跟随浏览器语言。

### 持久化

建议使用单独的 `localStorage` 键，例如：

- `hagsyn_locale`

---

## 五、UI 放置方案

### 控件位置

语言切换控件应放在现有顶部操作区中，靠近 `themeSwitcher` 与用户菜单，不新增单独页面。

这符合当前工作台壳层规则，也不会把一个基础设置做成新的流程入口。

### 控件形式

建议使用一个紧凑的 segmented control 或双按钮切换：

- `中文`
- `EN`

要求：

1. 视觉上服从现有深色工具壳风格
2. 当前语言有明确 active 状态
3. 键盘可聚焦
4. 不遮挡主题切换与用户菜单

### 页面语言属性同步

切换后应同步更新：

- `document.documentElement.lang`

从而让页面语言元信息与实际显示语言一致。

---

## 六、文案组织方式

### 字典结构

建议新增集中翻译资源，例如：

- `frontend/assets/js/i18n/messages.js`
- `frontend/assets/js/i18n/index.js`

字典 key 应按语义组织，而不是按页面截图组织。

例如按以下分组：

- `nav.*`
- `page.*`
- `tool.videoCompress.*`
- `tool.vttSubtitle.*`
- `tool.videoSubtitleBurn.*`
- `auth.*`
- `userMenu.*`
- `modal.*`
- `toast.*`
- `settings.*`
- `common.*`

### 取值原则

1. 统一使用稳定 key
2. 组件与视图只依赖 key，不直接关心具体语言文本
3. 对需要拼接动态值的场景，使用简单模板插值，不在业务代码中手写不同语言句式碎片

### 首版覆盖面

首版应覆盖用户看得到且会频繁接触的核心文案：

1. 左侧导航
2. 页面标题和副标题
3. 工具卡片标题、状态、摘要、模式名
4. 工具工作区中的上传区、模式区、按钮、结果卡片、空状态
5. 登录/注册视图
6. 用户菜单
7. 存储策略面板中的前端文案
8. Modal 与 Toast 文案

暂不强求一次性清零所有硬编码字符串，但新增与核心路径上的既有文案应优先收口到字典。

---

## 七、代码结构建议

推荐在现有前端结构下新增：

```txt
frontend/assets/js/i18n/
├── index.js
└── messages.js
```

职责建议如下：

### `messages.js`

负责：

- 定义 `zh-CN` / `en` 文案字典

### `index.js`

负责：

- 支持语言常量
- 默认语言解析
- `getLocale()`
- `setLocale()`
- `t(key, params?)`
- `subscribeLocaleChange()` 或等价刷新机制

### 现有模块改造原则

1. `config.js` 中与界面展示相关的静态标签应改为可翻译 key 或延迟取值
2. `app.js` 中页面标题、Modal、Toast、状态文本改为通过 `t()` 生成
3. `views/**`、`tools/**`、`components/**` 中所有核心用户可见文案逐步改为 key 驱动
4. 不在多个文件中复制 locale 判定逻辑

---

## 八、渲染与刷新策略

当前前端已有中心化渲染入口，因此首版建议使用“语言切换后触发整体重新渲染”的方式，而不是局部 DOM 打补丁。

推荐做法：

1. 切换语言后更新全局 locale 状态
2. 写入 `localStorage`
3. 重新渲染当前页面与当前工具工作区
4. 同步刷新导航、标题、右侧上下文、Modal、Toast 等依赖当前语言的区域

推荐理由：

1. 当前应用规模较小
2. 已有路由驱动和视图渲染逻辑
3. 这样比维护大量局部文本替换更稳定

---

## 九、兼容性与失败处理

需要考虑以下边界：

1. `localStorage` 中出现不支持的 locale 值时，应忽略并回退到浏览器语言策略
2. 翻译 key 缺失时，首版可回退到 key 本身或默认语言文案，但不能让页面直接报错
3. 切换语言后当前工具状态不应丢失，例如已选文件状态、当前路由、当前工具页应尽量保留
4. 不应把后端返回的英文错误文本错误地再做二次翻译猜测

---

## 十、测试与验证要求

根据当前项目规则，本次前端基础能力改动完成后至少需要以下验证：

### 自动检查

1. `node --check` 覆盖受影响的前端 JS modules
2. 前端最小结构/行为测试，至少覆盖：
   - 浏览器语言默认判定
   - 本地持久化优先级
   - 手动切换后 locale 更新
   - `t(key)` 的基础回退行为

### 真实交互验证

至少验证以下路径：

1. 首次访问时按浏览器语言显示正确界面
2. 用户手动从中文切到英文
3. 刷新页面后仍保持用户已选语言
4. 进入 `Tools` 具体工具工作区后，标题、按钮、结果区和说明文案同步切换
5. 语言切换不会破坏主题切换、登录流程和工具入口

---

## 十一、实施顺序建议

建议按以下顺序实现：

1. 建立 `i18n` 模块与字典
2. 接入全局 locale 状态与默认语言判定
3. 在顶部操作区加入语言切换控件
4. 改造导航、页面标题、副标题
5. 改造登录视图、用户菜单、Modal、Toast
6. 改造 `Tools` 列表与三个现有真实工具工作区
7. 做脚本检查、最小行为测试与真实交互验证

---

## 十二、推荐结论

本次前端国际化应作为一个小而完整的基础能力改造推进，重点是：

1. 保持当前工作台壳层不变
2. 先做 `zh-CN` / `en` 双语
3. 先把浏览器语言探测、手动切换和本地持久化跑通
4. 先覆盖核心用户路径的前端文案
5. 不把范围扩到后端国际化或前端框架重构

如果按这个设计实施，Hagsyn 将获得一个对当前本地工具工作台足够实用、且后续可继续扩展的前端 i18n 基础。
