# Hagsyn Module Map

## 文档目标

从产品职责角度梳理 Hagsyn 当前的模块地图，明确每个模块的输入、输出、核心页面角色和近期建设重点。

## 模块总览

当前 Hagsyn 可按职责划分为四个层次：

1. 工作台骨架层
2. 工具执行层
3. 知识沉淀层
4. 支撑能力层

## 1. 工作台骨架层

这一层负责提供统一的产品外壳与导航框架。

包含模块：

- `Dashboard`
- 一级导航
- 全局布局与状态区域

主要职责：

- 让所有能力都落在同一产品壳内
- 提供稳定的访问路径
- 承担模块之间的组织关系

近期重点：

- 保持导航稳定
- 保持页面角色清晰
- 不让新功能破坏既有模块分工

## 2. 工具执行层

这一层是 Hagsyn 当前最重要的产品层，直接承载真实工具。

包含模块：

- `Tools`
- 工具详情区
- 工具输入表单
- 工具执行与结果返回链路

当前核心工具：

- 视频压缩

### 输入

- 用户上传的真实文件
- 工具参数，例如压缩模式

### 输出

- 处理后的真实文件
- 工具执行状态
- 下载入口

### 近期重点

- 持续增强视频压缩这条真实链路
- 保持 Tools 页面能容纳更多真实工具
- 统一工具卡片、工具工作区和结果区域的产品语义

## 3. 知识沉淀层

这一层对应 Hagsyn 的 Knowledge 主线，用于未来承接由真实使用场景沉淀出来的对象、关系和路线。

包含模块：

- `Nodes`
- `Graph`
- `Roadmaps`

### Nodes

角色：

- 承载知识对象本体
- 未来存放与工具相关的场景、经验、资源、问题、方案等

当前状态：

- 保留结构
- 不主动灌 demo 数据

### Graph

角色：

- 承载对象之间的关系表达
- 未来展示“某个工具适用于什么场景、依赖什么经验、关联什么输出”

当前状态：

- 保留结构
- 不为图而图

### Roadmaps

角色：

- 承载阶段性建设路径
- 未来可用于工具接入路线、知识整理路线或某类任务解决路线

当前状态：

- 保留结构
- 等真实场景驱动

### 近期重点

- 保护 Knowledge 层的模块边界
- 暂不追求内容体量
- 明确这些模块未来是承接真实沉淀，而不是展示概念

## 4. 支撑能力层

这一层不是用户直接感知的主模块，但对产品长期可用性有支撑作用。

包含内容：

- 本地鉴权
- FastAPI API 服务
- SQLite 数据存储
- `ffmpeg` 能力依赖
- 文档与规范体系

### 作用

- 为 Tools 提供真实执行能力
- 为后续模块扩展提供可维护的工程基础
- 为产品、标准和 UX 三条文档主线提供对齐依据

## 模块关系图

```txt
Dashboard
  -> Tools
     -> Video Compress Workspace
     -> Future Real Tools
  -> Nodes
  -> Graph
  -> Roadmaps

Support Layer
  -> Auth / API / Storage / ffmpeg / Docs
```

## 模块边界说明

### Dashboard 不替代工具页

`Dashboard` 可以展示入口和状态，但不应承载完整工具操作逻辑。

### Tools 不伪装成知识库

`Tools` 的本质是“做事”，不是“罗列概念”。

### Knowledge 不抢当前主线

`Nodes / Graph / Roadmaps` 的意义是长期沉淀，不应在当前阶段反客为主。

### 支撑层不直接暴露为产品卖点

本地鉴权、数据库、`ffmpeg` 等是产品底座，不需要在产品层被包装成独立模块叙事。

## 当前模块地图结论

Hagsyn 当前的模块地图应围绕一个清晰判断展开：

- 骨架要稳定
- Tools 要先做深
- Knowledge 要有位置但保持克制
- 支撑层要足够稳，保证真实工具长期可用

只要这四层关系不乱，后续产品扩展就能持续落在同一条主线上。
