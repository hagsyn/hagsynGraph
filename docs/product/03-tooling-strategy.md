# Hagsyn Tooling Strategy

## 文档目标

定义 Hagsyn 在 `Tools` 主线上的建设策略，明确什么样的能力可以进入 `Tools`，以及工具如何在当前工作台中持续扩展。

## 核心判断

Hagsyn 当前阶段最重要的不是“有多少模块”，而是 `Tools` 模块里是否持续出现真实可用的能力。

因此，`Tools` 不是功能展示区，而是产品价值的第一落点。

## 什么是 Hagsyn 的真实工具

进入 `Tools` 的能力，至少要满足以下四个条件：

1. 有明确输入
2. 有真实处理过程
3. 有可验证输出
4. 用户可以独立完成一次完整操作

如果某项能力只有概念说明、假按钮、占位卡片或依赖示例数据撑场，它就不应算作 Hagsyn 当前阶段的正式工具。

## 当前工具策略

### 当前主工具：视频压缩

视频压缩是 Hagsyn 当前第一条已经成立的真实工具链路。

它具备完整闭环：

- 上传真实视频文件
- 选择压缩模式
- 执行本地压缩
- 获取输出文件
- 下载结果

这一工具的意义不仅在于“多了一个功能”，还在于验证了 Hagsyn 可以作为本地 AI/开发者工作台去承载真实任务。

### 当前策略结论

当前 `Tools` 主线应围绕视频压缩先做稳，而不是急于在页面上并排摆放很多尚未成形的工具卡。

## 工具接入标准

后续新增工具时，建议统一通过以下判断：

### 1. 是否解决真实任务

工具要对应一个实际问题，而不是抽象能力标签。

### 2. 是否能在本地工作台内完成闭环

工具应尽量在当前产品壳内完成输入、执行、结果展示和下载或复制，不依赖额外跳转拼凑流程。

### 3. 是否与当前产品用户类型一致

Hagsyn 当前更像开发者/AI 工作者的个人工作台，因此优先接入能直接提升日常效率的工具。

### 4. 是否值得长期维护

不是所有一次性小脚本都要进入 `Tools`。只有那些会被反复使用、值得拥有稳定入口和交互的能力，才适合产品化。

## 不建议进入 Tools 的内容

以下内容当前不建议直接放进 `Tools`：

- 纯概念说明页
- 靠 demo 数据展示的能力卡
- 没有执行链路的未来规划项
- 更适合作为知识条目的对象集合

这类内容如果确实需要记录，后续更适合进入 `Nodes` 或其他 Knowledge 主线容器。

## 工具页产品模式

Hagsyn 的 `Tools` 页面后续应统一采用以下产品模式：

### 工具目录

展示当前已经接入的真实工具，帮助用户快速选择任务。

### 工具工作区

在当前壳内完成输入、执行、进度反馈和结果展示。

### 结果区域

明确呈现输出物、下载方式和错误反馈，而不是只弹一句“已完成”。

### 说明区域

用于说明工具用途、输入要求、参数含义和注意事项，但不喧宾夺主。

## Tools 与 Knowledge 的衔接策略

`Tools` 不是独立飞地，后续它会成为 Knowledge 的真实来源之一。

可能的衔接方向包括：

- 某个工具沉淀出稳定的使用经验后，形成 `Nodes`
- 工具之间的组合关系未来可以进入 `Graph`
- 工具接入顺序和使用路径未来可以进入 `Roadmaps`

但这个衔接应在真实使用足够多之后发生，而不是先造一套抽象结构倒逼工具去适配。

## 工具扩展节奏建议

### Phase 1：单工具做稳

先确保视频压缩在体验和稳定性上可持续使用。

### Phase 2：补齐工具接入规范

形成统一的卡片结构、工作区模式、结果区规则和接入判断标准。

### Phase 3：按真实场景增加工具

只在出现明确高频需求时新增第二、第三个工具。

### Phase 4：从工具使用中倒逼知识沉淀

当工具数量和使用频率足够高时，再把经验组织进 `Nodes / Graph / Roadmaps`。

## 当前策略结论

Hagsyn 的 `Tools` 主线应坚持“少而真”的策略。

在当前阶段，最正确的方向不是尽快做出一个看起来丰富的工具市场，而是持续积累一组真的能被反复使用的工具工作区，并让它们成为整个产品体系最坚实的基础。
