# Bug Fix Workflow

## 适用场景

适用于 Hagsyn-Graph 中已经存在的能力出现异常，需要完成复现、定位、修复与回归验证的事项，包括：

- 接口报错、上传失败、压缩失败、下载失败
- 页面行为异常、状态文案与真实状态不一致
- 既有功能回归、边界条件处理错误
- 由测试、手工验证或用户反馈发现的缺陷

不适用于新能力建设；那类任务应改走 `feature-development-workflow.md`。

## 前置检查

1. 先拿到可复现的现象：输入条件、操作步骤、报错信息、预期与实际差异。
2. 按需阅读：
   - `docs/standards/**`：接口、数据、工程规范
   - `docs/product/**`：真实行为预期与模块职责
   - `docs/ux/**`：若问题涉及状态文案、交互反馈或页面结构
3. 判断是否需要下层 skill：
   - 缺陷背后暴露产品边界、假完成度或模块落点问题时，调用 `hagsyn-product-guard`
   - 问题涉及工作区布局、工具视图、状态区或空状态时，调用 `hagsyn-ui-workspace-pattern`
   - 回归面、验证策略、报告格式不清时，调用 `hagsyn-testing-council`
4. 在动实现前先锁定“首条硬失败点”，不要直接凭猜测修改代码。

## 执行步骤

1. 复现缺陷，并记录最小复现路径。
2. 定位根因，明确是接口逻辑、数据条件、状态同步、前端脚本还是 UI 文案问题。
3. 先补一个会失败的回归测试或等价的失败验证：
   - 后端缺陷优先补接口 / service 层测试
   - 前端缺陷至少补结构或脚本验证，并准备真实交互回归点
   - 若当前仓库难以自动化，也要先形成可重复的失败验证步骤
4. 实施最小修复，只改与根因直接相关的区域。
5. 重新运行受影响验证：
   - 先看回归测试或失败验证是否转绿
   - 再看相邻受影响能力是否仍正常
6. 若问题涉及用户可见交互、状态切换或页面反馈，做真实页面点击或等价真实交互验证。
7. 在准备宣称修复完成前，调用 `hagsyn-review-council` 做最终交付审查；若缺陷修复同时触及多个模块或治理面，可在中途先做一次轻量预审。
8. 记录测试报告或缺陷修复验证摘要，至少包含：
   - 缺陷现象
   - 根因
   - 回归测试 / 验证动作
   - 修复后结果
   - 剩余风险
9. 执行 stop hook 判断：
   - 只要复现、根因、回归、报告中还有缺口，就继续补完
   - 不允许停在“看起来修好了，但还没把回归链路跑完”

## 自校验步骤

1. 是否先复现并定位了根因，而不是直接试错式改代码？
2. 是否在修复前准备了失败中的回归测试或可重复失败验证？
3. 修复后是否真正回跑了相关验证，而不是只靠代码阅读判断？
4. 若问题影响前端可见行为，是否做了真实交互验证？
5. 是否写下了测试报告或验证摘要，能解释“为什么现在算修好”？
6. 是否已经经过 `hagsyn-review-council` 终审，或明确说明当前仍处于预审/未收口状态？
7. 是否仍存在未解释的副作用、未覆盖边界或回归空洞？

## 常见失败点

- 没复现就开修，最后只是碰巧掩盖现象，没有解决根因。
- 修复前没有失败中的回归验证，导致“通过”无法证明问题真被覆盖。
- 修完只看主路径，不看相邻影响面，结果引入新的回归。
- 前端缺陷只改文案或逻辑，没有做真实页面验证。
- 未做最终 review 就直接宣布“问题已解决”。
- 停在口头结论，没有留下测试报告、根因说明和剩余风险。
