# Feature Development Workflow

## 适用场景

适用于 Hagsyn-Graph 中会新增或明显扩展真实能力的开发事项，包括：

- 新工具、新接口、新页面区块
- 现有视频压缩链路中的新交互或新业务能力
- 会影响 `Tools` / `Knowledge` 落点、页面结构、验证链路的功能开发

不适用于纯缺陷修复；那类任务应改走 `bugfix-workflow.md`。

## 前置检查

1. 先确认需求是“真实可用能力”而不是展示性补丁，避免偏回 demo 驱动。
2. 按需阅读：
   - `docs/product/**`：产品定位、模块职责、范围边界
   - `docs/standards/**`：工程结构、接口、数据和文档规范
   - `docs/ux/**`：若涉及 UI、工作区壳、交互或空状态
3. 判断是否需要先调用下层 skill：
   - 需求边界或模块归属不稳时，调用 `hagsyn-product-council`
   - 出现范围膨胀、假数据、`Tools` vs `Knowledge` 漂移风险时，调用 `hagsyn-product-guard`
   - 涉及工作区壳、工具视图、右侧详情区或空状态时，调用 `hagsyn-ui-workspace-pattern`
   - 涉及测试策略、覆盖面或报告格式判断时，调用 `hagsyn-testing-council`
4. 明确本次功能的最小闭环、影响面和验证面，避免边实现边改目标。

## 执行步骤

1. 用一句话定义功能目标，并明确它服务的真实用户动作。
2. 根据前置检查结果确认模块落点、接口边界和 UI 边界。
3. 若仓库内已有对应 spec / plan，先按其约束执行；若缺失且任务复杂，先补设计与实现计划。
4. 先补测试设计：
   - 后端能力先定义 API / service 层测试目标
   - 前端能力先定义结构检查、脚本检查和真实交互验证点
   - 跨端能力先定义端到端闭环验证
5. 实现功能，保持改动贴近现有模块和文件边界，不顺手扩散到无关区域。
6. 跑核心验证：
   - 后端改动：至少覆盖受影响接口、关键业务路径、失败分支
   - 前端改动：至少跑脚本语法检查和受影响交互检查
   - 用户可见交互变化：做真实页面点击或等价真实交互验证
7. 若验证暴露范围漂移、状态文案失真或工作区模式破坏，回到相应下层 skill 复核后再收口。
8. 在准备宣称完成前，调用 `hagsyn-review-council` 做最终交付审查；若任务跨多个模块、公共接口或治理面，可在实现中途先做一次轻量预审。
9. 记录测试报告或最小验证报告，至少包含：
   - 改动目标
   - 验证命令或验证动作
   - 通过 / 失败结果
   - 剩余限制与未覆盖项
10. 执行 stop hook 判断：
   - 若当前 workflow 仍有未完成的验证、报告或收口动作，继续完成
   - 只有在当前链路已经到达可交付状态时才结束

## 自校验步骤

1. 是否已经读过与本次功能相关的 `docs/product`、`docs/standards`、`docs/ux`？
2. 是否在需要时调用了 `council / guard / ui / testing`，而不是凭印象跳过？
3. 是否有与改动面匹配的测试证据，而不是只说“理论上可以”？
4. 若改动影响前端，是否做了真实交互验证，而不只是静态阅读代码？
5. 是否已经形成测试报告或验证摘要，可让后续人复核？
6. 在进入完成结论前，是否已经过 `hagsyn-review-council` 的终审或说明为何尚未到终审阶段？
7. 是否避免把未完成事项伪装成“已完成”后提前停住？

## 常见失败点

- 只读了实现文件，没有先读产品、标准、UX 文档，导致方向或接口命名偏移。
- 新功能未做范围判断，结果把 `Knowledge`、展示壳或未来规划混进本次实现。
- 有前端改动却只跑接口或 `node --check`，没有真实点击验证。
- 测试只看通过，不记录验证面、限制和缺口，后续无法追溯。
- 没有经过最终 review 就直接宣称“功能完成”。
- 写完功能就停在“已修改代码”，没有完成测试报告和 stop hook 收口。
