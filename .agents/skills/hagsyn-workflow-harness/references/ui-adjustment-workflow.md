# UI Adjustment Workflow SOP

## 适用场景

当任务涉及以下任一情况时使用本 workflow：

- 调整 `frontend/index.html` 的工作区壳层、布局、导航、面板或模块 framing
- 修改工具主流程中的输入、执行、结果、下载、右侧上下文区域
- 调整开发者工具风格、交互状态、空状态或页面可用性
- 需要确认 UI 改动没有把产品从真实工具工作区带偏成展示页

如果任务是纯后端、纯数据层或纯文档修改，不使用本 workflow。

## 前置检查

1. 确认任务目标指向真实 UI 行为，而不是抽象的视觉想法堆叠。
2. 先读取相关产品与 UI 约束，至少覆盖：
   - `docs/product/**`
   - `docs/ux/**`
   - `.agents/skills/hagsyn-ui-workspace-pattern/**`
3. 确认当前改动范围，避免误改 `README.md`、`AGENTS.md`、测试文档或无关模块。
4. 确认本地可用验证条件：
   - 前端静态服务可启动
   - 若涉及后端联动，后端接口可访问
   - 本机可执行 `node --check`
5. 写改动前先查看目标文件当前状态，避免覆盖他人正在进行的调整。

## 执行步骤

1. 先定义这次 UI 调整的最短成功路径，例如“进入页面 -> 输入/选择 -> 执行动作 -> 查看结果”。
2. 将改动限制在当前页面壳层和真实工具闭环内，不引入 marketing 化布局、假卡片墙或演示型信息块。
3. 如涉及工作区结构，保持左导航 / 中操作 / 右上下文的职责清晰；如是局部调整，也要保证主操作区优先级最高。
4. 实现 UI 调整时，优先复用现有样式语法、状态组织和控件关系，不额外发明一套新页面语言。
5. 完成代码修改后，按顺序执行三类必做验证：
   - 壳测试：确认页面主壳可正常返回，核心 DOM 结构和关键入口仍存在
   - `node --check`：抽取并检查内嵌脚本语法，防止页面因脚本截断或语法错误直接失效
   - 网页点击验证：实际打开页面，点击关键路径，确认主流程可操作、状态切换正常、无明显遮挡或空白
6. 若点击验证发现布局漂移、按钮无效、状态错位或结果区失真，先回到实现层修复，再重新跑完整验证，不只补跑单项。
7. 在准备收口前，调用 `hagsyn-review-council` 做最终交付审查；若 UI 调整同时触及工作区壳层、公共交互或治理面，可先做一次轻量预审。
8. 收口时记录本次改动影响的页面区域、验证结果和仍存在的边界风险。

## 自校验步骤

1. 是否仍保持真实工具工作区，而不是滑向 landing page、showcase 或假 dashboard。
2. 主任务路径是否更清楚，且没有因为新增说明、装饰或面板而被打断。
3. 是否已经完成壳测试，并确认页面主壳、关键入口和主要区域正常存在。
4. 是否已经执行 `node --check`，且脚本语法检查通过。
5. 是否已经做网页点击验证，并覆盖至少一个完整主路径。
6. 点击过程中是否确认了关键按钮、状态切换、结果显示、下载或后续动作可达。
7. 是否已经经过 `hagsyn-review-council` 终审，或明确说明当前只是高风险预审阶段？
8. 是否避免覆盖或回滚他人改动，并且只修改本次任务需要触达的区域。

## 常见失败点

- 只看静态代码或截图，没有做实际网页点击验证。
- 改完样式后没跑 `node --check`，导致内嵌脚本断裂，页面只剩外壳。
- 把“优化 UI”做成大段展示内容，真实工具入口反而变弱。
- 只验证局部控件，不验证完整主路径，结果交付后才发现流程断点。
- 没有经过最终 review 就把 UI 改动当作可交付结果。
- 为了让页面“更满”加入假数据、无关状态卡片或装饰性右栏内容。
- 修改范围失控，顺手改到无关文档、说明文件或其他 skill。
