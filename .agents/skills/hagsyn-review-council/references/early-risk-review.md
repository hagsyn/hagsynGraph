# Early Risk Review SOP

## 适用场景

当任务尚未收口，但已经命中高风险条件，且主 agent 需要在不中断整体推进的前提下尽早识别返工成本高的问题时使用。

典型触发包括：

- 跨多个模块、前后端联动或共享接口变更
- 涉及 `docs/product/**`、`docs/standards/**`、`.agents/skills/**`
- 涉及主工具链路、工作区壳层或共享数据结构
- 一旦方向错了，后续返工成本明显偏高

## 前置检查

1. 明确当前任务还处于实现中途，而不是最终收口。
2. 标出本次只预审哪些高风险点，不把预审误做成完整终审。
3. 确认主 agent 当前最关心的是哪类返工风险：
   - 模块边界错位
   - 接口设计偏移
   - workflow 收口链断裂
   - 治理文档遗漏
4. 确认预审后主流程仍会继续推进，不把每次中途 review 都变成阻塞门。

## 执行步骤

1. 先说明本次 review 是“高风险轻量预审”，不是最终交付结论。
2. 只聚焦最可能造成大返工的点，例如：
   - 模块落点是否正确
   - 公共接口或数据语义是否稳定
   - 文档/skill/标准是否需要同步设计
   - 当前验证计划是否明显不足
3. 输出时按优先级给出：
   - 立即需要调整的高风险问题
   - 可以继续推进但要带着观察的风险
   - 建议在最终 review 前补齐的材料
4. 控制输出体量，避免轻量预审演变成完整全量审查。
5. 明确提醒：最终收口前仍需执行 `final-delivery-review.md`。

## 自校验步骤

1. 是否真的只做高风险预审，而没有把中途 review 做成完整终审？
2. 是否把注意力放在返工成本最高的问题，而不是枝节优化建议？
3. 是否保留了主流程流畅度，没有因为预审把执行节奏切得过碎？
4. 是否明确说明哪些项留到最终 review 再统一判定？
5. 预审结论是否足够具体，能指导主 agent 立刻调整方向？

## 常见失败点

- 中途 review 过度展开，变成每改一点都来一次完整审查。
- 只给泛泛提醒，没有指出真正高风险的返工点。
- 把普通小建议也升格成阻塞项，拖慢主流程。
- 预审后没有提醒仍需做最终终审，导致流程停在半程。
- 没区分“立即要改”和“最终收口前再补”，让执行顺序混乱。
