# Governance Surface Review SOP

## 适用场景

当一次任务明显触及治理面资产，需要重点审查文档、标准、skill、索引、配置说明与实现是否一致时使用。

典型触发包括：

- 修改 `docs/product/**`、`docs/standards/**`、`docs/ux/**`
- 修改 `.agents/skills/**`
- 修改 `README.md`、`AGENTS.md`、`docs/INDEX.md`
- 修改会影响项目对外口径的配置说明、运行约束或流程规则

## 前置检查

1. 明确本次治理面改动涉及哪些资产和它们各自的职责。
2. 确认是否已有对应实现或行为变化作为事实源，避免只改口径不改实际，或只改实际不改口径。
3. 若涉及 skill，先确认是否还需要调用 `hagsyn-skill-review`。
4. 确认本次 review 的核心问题是“一致性与治理完整性”，而不是实现性能或视觉细节。

## 执行步骤

1. 先列出治理面改动的清单，例如：
   - 哪些索引被更新
   - 哪些标准被补充
   - 哪些 skill 被新增或路由调整
2. 检查这些变更是否彼此一致：
   - 入口文档是否能找到新增能力
   - skill 名单、职责描述、路由说明是否一致
   - 标准中的约束是否和 skill 实际结构匹配
3. 检查实现与治理口径是否一致：
   - 文档里说“必须”的动作，skill 或 workflow 是否真的接上
   - skill 里说“默认调用”的场景，索引和总控是否能发现它
4. 检查是否有遗漏资产：
   - 新增 skill 但没进 `README.md` 或 `AGENTS.md`
   - 新增标准但没进 `docs/INDEX.md`
   - 新增路由但没更新总控 skill
5. 输出时明确说明：
   - 哪些治理面已同步完成
   - 哪些口径仍不一致
   - 是否可以作为新的项目基线继续使用

## 自校验步骤

1. 是否围绕“一致性、可发现性、治理完整性”来审查，而不是偏离到无关实现细节？
2. 是否检查了新增或修改项在入口索引、标准和 skill 路由上的可发现性？
3. 是否区分了“结构已接上”和“只是文档提到了”这两种不同状态？
4. 若存在漏同步资产，是否明确列成问题而不是默认忽略？
5. 结论是否能回答“这次治理面改动现在能不能作为新基线”？

## 常见失败点

- 新增了 skill，但没更新索引、README、AGENTS 或总控路由。
- 改了标准文档，但 skill 实际结构并未跟上。
- 只检查文档字面是否存在，没有检查是否真的可发现、可执行。
- 把治理面 review 变成语气润色，而不是一致性审查。
- 发现口径冲突后没有指出哪个文件应作为事实源。
