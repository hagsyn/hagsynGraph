# Final Delivery Review SOP

## 适用场景

当 Hagsyn-Graph 中的功能开发、bug 修复、UI 调整、skill 治理或其他重要变更已经完成实现与基础验证，准备进入最终收口时使用。

典型触发包括：

- 主 agent 准备宣称任务完成
- workflow 已跑到测试、报告和说明同步阶段
- 变更横跨代码、文档、skill、配置或验证材料中的两类及以上资产

## 前置检查

1. 确认本次 review 的改动范围，至少列出受影响的代码、文档、skill、配置或报告文件。
2. 收集本次已完成的验证证据：
   - 测试命令或测试结果
   - 前端脚本检查
   - 页面点击验证
   - 测试报告或治理摘要
3. 确认是否已有下层专项结论可引用：
   - `hagsyn-testing-council`
   - `hagsyn-skill-review`
   - 其他与本次任务直接相关的 skill 输出
4. 明确当前任务的交付口径：是“完全可收口”，还是“允许带已说明风险交付”。

## 执行步骤

1. 先定义审查范围，说明这次 review 覆盖哪些改动面。
2. 从实现面审查：
   - 是否存在明显逻辑缺陷
   - 是否有回归风险
   - 是否有边界条件未解释
   - 是否有无关扩散改动
3. 从治理面审查：
   - 文档是否和实际改动同步
   - skill、配置、索引或标准是否遗漏更新
   - 变更是否绕开了既有规则或 workflow
4. 从验证面审查：
   - 测试证据是否与改动面匹配
   - 用户可见改动是否有结构/脚本/真实交互验证
   - skill 或治理类改动是否做了对应自检
5. 输出统一结论，至少包含：
   - 审查范围
   - 发现的问题
   - 必须修复项
   - 剩余风险或测试缺口
   - 收口结论
6. 若存在阻塞性问题，不要用笼统语言淡化，直接给出“需修正后再收口”。

## 自校验步骤

1. 是否先列问题与风险，而不是先给总体好坏判断？
2. 是否同时覆盖了代码、文档、skill、配置、验证证据中与本次改动相关的部分？
3. 若某项验证缺失，是否明确写成缺口，而不是默认为通过？
4. 是否给出了明确收口结论，而不是“基本可以”“大致没问题”这类模糊表述？
5. 若没有发现阻塞性问题，是否仍写清了残余风险和未覆盖边界？

## 常见失败点

- 只看代码 diff，不看文档、skill、配置或验证同步情况。
- 只复述测试通过，没有判断这些测试是否真的覆盖了改动面。
- review 结论只有“LGTM”式表态，没有问题清单、风险和收口判断。
- 明明存在阻塞性问题，却用“后续可优化”弱化。
- 没有说清审查范围，导致结论看起来像泛泛检查。
