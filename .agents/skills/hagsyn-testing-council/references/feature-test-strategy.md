# Feature Test Strategy SOP

## 适用场景

当新增或明显扩展一个功能时使用，例如新工具接入、新页面工作区、新接口返回结构、新下载流程或新交互链路。

## 前置检查

1. 列出本次功能新增了哪些真实用户路径
2. 区分后端行为变化与前端可视变化
3. 确认哪些地方可以用自动测试覆盖，哪些地方需要额外交互验证

## 执行步骤

1. 为后端新增或调整的行为补 API 级测试
2. 为前端新增或调整的结构补壳测试或结构断言
3. 若功能涉及用户可见状态变化，检查文案、状态名和结果语义是否与实现一致
4. 若有新下载或新结果文件，检查返回元信息和下载路径
5. 完成功能后在 `docs/testing/reports/` 下写一份本轮测试报告
6. 检查页面里的状态文案是否和真实可用性一致，不把“已可用”写成“规划中”，也不把未落地能力写成“已可用”

## 自校验步骤

1. 是否为每条新增用户路径至少补了一类自动测试
2. 是否覆盖了后端行为和前端结构中变化最大的部分
3. 是否没有只靠“手测看起来没问题”就收口
4. 是否已生成测试报告
5. 工具卡状态、模块状态和结果文案是否与真实实现状态一致

## 常见失败点

- 新功能做完只靠自己点几下页面
- 只补后端测试，不补前端结构验证
- 结果语义变化了，但测试仍只验证旧字段存在
- 忘记沉淀测试报告
- 页面状态标签与真实功能状态不一致，还要靠用户人工指出
