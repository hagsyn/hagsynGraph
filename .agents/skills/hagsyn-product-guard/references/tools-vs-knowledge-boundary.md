# Tools vs Knowledge Boundary SOP

## 适用场景

当任务涉及新能力归属、模块扩展、导航信息架构调整、`Tools` 与 `Knowledge` 取舍，或准备把某项能力放入知识侧时使用。

## 前置检查

1. 确认待评估能力的真实输入、操作过程和输出结果
2. 确认这项能力是否已经有真实用户场景，而不是概念性补位
3. 确认 `Knowledge` 侧是否已有真实内容源、维护动作或操作需求

## 执行步骤

1. 先判断该能力是否属于可执行工作流：
   - 有输入
   - 有配置或操作
   - 有运行过程
   - 有结果交付
2. 如果是，默认优先归入 `Tools`
3. 只有在以下条件同时成立时，才考虑深化 `Knowledge`：
   - 存在真实使用场景
   - 存在真实内容源
   - 存在明确操作任务，而非只读陈列
4. 若条件不足，把 `Knowledge` 保持在 shell stage：
   - 轻量入口
   - 占位说明
   - 不承诺未验证能力
5. 输出结论时，明确说明：
   - 为什么放在 `Tools` 或 `Knowledge`
   - 是否只是保留壳层
   - 哪些证据仍然缺失

## 自校验步骤

1. 是否把可执行能力优先留在 `Tools`
2. 是否避免因为“产品看起来更丰富”而提前做重 `Knowledge`
3. 若建议扩展 `Knowledge`，是否给出了真实场景和内容来源证据
4. 结论是否避免模糊话术，而是清楚说明归属原因与保留边界

## 常见失败点

- 把工具型能力挪去 `Knowledge` 只是为了信息架构好看
- 在没有真实内容源时先做知识卡片、图谱或目录树
- 用“以后可能有用”作为扩展 `Knowledge` 的唯一理由
- 没有证据就把壳层入口说成正式模块
