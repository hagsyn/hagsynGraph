# Priority And Staging SOP

## 适用场景

当任务涉及需求排序、分阶段落地、判断“先做什么后做什么”、控制范围膨胀，或需要把一个提议拆成当前阶段与后续阶段时使用。

典型触发包括：

- 一个需求同时包含 MVP、产品规则、未来扩展三层内容
- 任务想同时推进 `Tools`、工作台壳和 `Knowledge`
- 用户提出的方向合理，但当前仓库阶段只适合先落一部分
- 需要回答“为什么这项能力现在不做”或“为什么只做第一阶段”

## 前置检查

1. 先确认当前阶段基线：Hagsyn 现在以真实工具为主，首要目标是把本地可执行工具做稳
2. 把待办内容按类型拆开：
   - 真实工具闭环
   - 工具产品化规则
   - 工作台壳层稳定性
   - `Knowledge` 结构保留或深化
3. 检查每一项是否具备立即开工的证据：
   - 真实场景
   - 明确输入输出
   - 当前用户价值
   - 不依赖 demo 数据
4. 标记会拉偏节奏的内容，例如：
   - 为了“看起来完整”补大面积占位模块
   - 先做复杂知识结构，等待未来内容填充
   - 一次性铺很多工具但没有完成闭环

## 执行步骤

1. 先按优先级把工作分成三层：
   - `Now`：直接增强当前真实工具路径或保障其稳定性的工作
   - `Next`：在 `Now` 稳定后，帮助新工具接入或统一产品规则的工作
   - `Later`：依赖真实使用积累、当前证据不足或容易 demo-driven 的工作
2. 判断某项工作能否进入 `Now`，至少要满足其中大部分条件：
   - 直接服务真实任务完成
   - 能在现有工作台内形成可验证结果
   - 不要求新增假数据或伪流程
   - 做完后用户价值立即可见
3. 对进入 `Next` 的事项，说明它依赖什么前提完成，例如：
   - 首个工具闭环稳定
   - 已形成统一工作区模式
   - 出现第二个真实工具接入需求
4. 对放入 `Later` 的事项，不是简单说“以后再说”，而要写清：
   - 当前为什么不做
   - 缺什么证据
   - 哪些现实信号出现后再启动
5. 如果一个提议同时含有可立即落地部分和过早部分，先裁出最小可执行阶段，保留后续阶段说明，但不要把它们混进当前交付
6. 输出优先级结论时，明确给出：
   - 当前阶段应该做的最小集合
   - 暂缓项列表
   - 每个暂缓项的进入条件

## 自校验步骤

1. `Now` 层是否紧贴真实工具价值，而不是被展示型内容挤占
2. 阶段划分是否清楚区分了“当前必要”与“未来可想”
3. 是否避免把 `Knowledge` 当作当前阶段的主价值来源
4. 是否避免为了路线图好看，把没有证据的事项硬塞进近期阶段
5. 输出结论后，执行团队是否能立刻知道先做什么、暂停什么、等待什么信号

## 常见失败点

- 把 roadmap 当成功能清单，一次性给每个模块都安排近期任务
- 用“顺手一起做掉”把当前任务扩成多阶段大包
- 把 `Knowledge` 深建设排到前面，只因为工作台里已经有对应导航
- 没有进入条件定义，导致“Later” 项目在下一轮又被原样拿出来推进
- 只给优先级标签，不说明当前为什么做、为什么不做
