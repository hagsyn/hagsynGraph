# Implementation Tradeoff SOP

## 适用场景

当任务涉及多个实现方案比较、需要在“先做真实闭环”与“先做通用抽象”之间取舍、评估是否值得引入新模块或更重结构时使用。

典型触发包括：

- 新功能有 2 个或以上可行实现路径
- 某方案更快落地，另一方案更通用但更重
- 方案会影响 `Tools` 主线、工作台壳层或 `Knowledge` 后续边界
- 提议中出现“顺手把底层一起抽象好”“先把未来能力预埋完整”这类说法

## 前置检查

1. 先写清楚这次要解决的真实任务是什么，不能只写“提升扩展性”或“架构更优雅”
2. 确认当前变更是否直接服务 Hagsyn 现阶段主路径，尤其是 `Tools -> 真实可执行工具`
3. 识别每个方案的用户可见收益、实现成本、维护成本和对现有壳层的影响
4. 判断方案是否依赖以下高风险前提：
   - 未来会有很多类似工具，但当前还没有真实接入计划
   - `Knowledge` 很快会进入深建设阶段
   - 需要 demo 数据或伪对象才能体现方案价值
5. 确认是否已有仓库内现成模式可复用，优先沿用而不是重造一套产品/工程语法

## 执行步骤

1. 先列出候选方案，至少写明：
   - 方案名称
   - 解决的问题
   - 需要改动的边界
   - 用户最终能得到什么真实结果
2. 对每个方案用同一组维度做对比：
   - 是否更快形成真实可用闭环
   - 是否会引入当前阶段用不上的抽象层
   - 是否会拉高 `Knowledge` 复杂度或制造伪完整感
   - 是否破坏现有工作台壳、工具工作区或产品语义
   - 后续扩展时是否能在现有基础上自然演进
3. 优先保留“更小但真实”的方案，只要它满足：
   - 可以直接解决当前任务
   - 不阻断后续演进
   - 不需要靠假设中的未来场景证明自己
4. 如果某个更重方案确实有必要，必须明确写出触发它的现实证据，例如：
   - 已确认的第二个真实工具接入需求
   - 已出现重复实现并造成维护问题
   - 当前实现已经阻碍用户完成主路径
5. 输出结论时，明确说明：
   - 推荐方案是什么
   - 为什么不是更重或更泛化的方案
   - 当前有意延后的部分是什么
   - 后续什么信号出现时再升级方案

## 自校验步骤

1. 推荐方案是否首先强化了真实工具闭环，而不是先强化概念完整度
2. 对比过程是否把“当前真实收益”放在“未来可能收益”之前
3. 是否明确压住了没有证据支撑的过早抽象、过早平台化或过早 Knowledge 深化
4. 输出结论时，是否讲清了为什么现在做小、哪些东西是刻意不做
5. 方案是否仍然保持后续可演进，而不是把系统锁死在一次性实现上

## 常见失败点

- 把“以后可能会有很多工具”当成现在就要做通用平台层的充分理由
- 为了抽象整齐，先引入当前只服务一个场景的复杂结构
- 方案比较只谈工程优雅，不谈当前用户能不能更快拿到真实结果
- 用 `Knowledge`、图谱、关系模型去包装尚未形成真实内容源的能力
- 没有说明延后项，最后把所有未来设想一起塞进当前版本
