# New Feature Evaluation SOP

## 适用场景

当任务涉及新增产品能力、扩展现有模块职责、评审某个想法是否值得进入实现，或需要先判断需求是否应进入当前 Hagsyn 范围时使用。

## 前置检查

1. 确认需求描述的是一个真实用户任务，而不是抽象概念补位。
2. 确认该需求的输入、关键操作和预期输出是否已经能说清楚。
3. 对照当前产品定位，确认该需求是否服务于本地单机版真实工具链路或其直接支撑能力。
4. 检查现有 `Dashboard / Tools / Nodes / Graph / Roadmaps` 中是否已有可承载的入口。

## 执行步骤

1. 先把需求压缩成一个最小任务表述：
   - 谁在用
   - 进入点是什么
   - 需要完成什么动作
   - 完成后拿到什么结果
2. 判断它是否增强当前真实主链路：
   - 是否直接提升现有工具可用性
   - 是否补足真实操作闭环中的缺口
   - 是否属于已验证需求的直接延伸
3. 若需求偏离当前主线，判断它是：
   - 应暂缓的远期想法
   - 仅保留轻量入口的预留能力
   - 需要缩小范围后再进入实现的能力
4. 判断该需求的实现深度：
   - 先做最小可用闭环
   - 只保留结构入口
   - 暂不进入当前迭代
5. 输出评审结论时明确说明：
   - 是否建议进入实现
   - 建议的最小范围
   - 为什么是现在做、现在不做，或只做壳层
   - 缺失了哪些证据或前提

## 自校验步骤

1. 结论是否围绕真实任务和真实结果，而不是围绕概念完整性。
2. 是否优先保护了当前 `Tools` 主线，而不是让新需求把重心带偏。
3. 是否给出了“现在做多少”的清晰边界，而不是只有笼统的支持或反对。
4. 是否避免把未来设想写成当前已确认范围。
5. 是否明确标出了仍需验证的用户场景、内容来源或工程前提。

## 常见失败点

- 把“看起来产品更丰富”当成需求通过的主要理由。
- 只讨论页面长什么样，没有说明真实输入、操作和输出。
- 没有缩范围，直接把想法放大成新系统或新主线。
- 用“以后可能会需要”代替当前场景证据。
- 没有写清楚是进入实现、只保留入口，还是明确暂缓。
