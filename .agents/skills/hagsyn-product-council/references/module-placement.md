# Module Placement SOP

## 适用场景

当任务涉及判断某项能力、页面、入口、对象或工作流应该落在 `Dashboard`、`Tools`、`Nodes`、`Graph`、`Roadmaps` 中哪一个模块，或需要决定它是否只保留壳层时使用。

## 前置检查

1. 确认待判断对象的核心职责是“执行任务”还是“承载知识/关系/路线”。
2. 确认它是否已经有真实输入、操作过程、结果交付或内容维护动作。
3. 确认当前现有模块中是否已有语义相近的承载位，避免平行造词。
4. 对照信息架构与模块地图，确认这次判断是否会影响一级模块语义稳定性。

## 执行步骤

1. 先按模块职责做第一轮归类：
   - `Dashboard`：总览、引导、状态汇总
   - `Tools`：真实执行型工作流
   - `Nodes`：知识对象本体
   - `Graph`：对象关系表达
   - `Roadmaps`：阶段路径与路线组织
2. 判断该能力是否满足 `Tools` 特征：
   - 有明确输入
   - 有配置或操作
   - 有执行过程
   - 有结果输出或交付
   满足时默认优先放入 `Tools`。
3. 若考虑放入 `Knowledge` 相关模块，再细分判断：
   - 对象本体归 `Nodes`
   - 关系表达归 `Graph`
   - 路径组织归 `Roadmaps`
4. 若证据不足以支撑深化 `Knowledge`，则只保留轻量壳层：
   - 保留入口
   - 保留职责说明
   - 不承诺未验证的深能力
5. 输出结论时明确说明：
   - 推荐模块
   - 不推荐放入的相邻模块及原因
   - 是正式落地还是壳层占位
   - 未来从壳层升级所需的触发条件

## 自校验步骤

1. 是否优先复用了现有模块，而不是制造新的并列分类。
2. 是否把执行型能力稳定留在 `Tools`，没有因为页面好看而误放到 `Knowledge`。
3. 若落入 `Knowledge`，是否说清楚是对象、关系还是路线，而不是语义混装。
4. 是否在证据不足时保持了壳层克制，而不是提前承诺成熟模块。
5. 结论是否同时写清了推荐落点、排除理由和升级条件。

## 常见失败点

- 把工具能力拆到 `Dashboard`，导致首页变成功能杂糅页。
- 把知识对象、关系、路线混成一个泛知识模块。
- 因为导航想更丰满，就把未验证能力塞进 `Nodes / Graph / Roadmaps`。
- 没有区分正式模块落地和壳层占位，导致后续实现边界失真。
- 明明已有现成模块可承载，却额外发明新入口或新分类。
